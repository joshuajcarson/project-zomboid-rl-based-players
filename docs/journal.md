## How to resume (state of the machine may differ, check first)
1. `git log --oneline -8` and read the top of this file.
2. Is a server running? `python -c "import socket;socket.create_connection(('127.0.0.1',17600),timeout=2)"` succeeds if so. Server boot takes about 5 minutes.
3. Never stop java by memory size (server and client are both big). Match command lines: the server has `rl-agent.jar`, rendered clients have `rl-agent-client`.
4. Client Lua edits (`mods/RLBridge/common/media/lua/client/*.lua`) need `scripts/install-mods.ps1 -Enable RLBridge` plus a server restart; `rl_bot_dev.lua` + `reload` is the no-restart iteration path.

## Validation gates (avoid investing in dead ends; added 2026-10-26 on the user's request)
A skill only counts as "learned" when all of these hold; otherwise spend the effort on fidelity, not on more training:
1. Fake-backend evaluation beats the scripted baseline or a clear threshold (greedy policy, 4+ episodes, matched spawns).
2. Transfer: the same checkpoint run with one REAL rendered client (backend="mixed", scripts/eval_transfer.py, 10+ episodes) reaches at least ~70% of the fake-only score on the same metric (final pair distance, damage taken). The real client must have the normal load (11 items, one bat, check `inv|user`) and the fake mover must be calibrated to the real runner's speed (scripts/measure_speed.py).
3. If gate 2 fails on two skills in a row, stop training and close the gap (speed, damage model, zombie behaviour, combat) before anything else.
Known fidelity gaps (2026-10-26): combat (real swings land weakly and staggered, fake kills for free: do not train fighting on the fake backend until fixed), zombie damage (synthetic bite rule vs real), zombie aggro/behaviour not compared, only one real client fits in RAM at a time (15.8 GB): a recording with 4 real clients needs a smaller client footprint or another machine.

## Task queue (top first)
000000. USER POINT (2026-10-26): light and visibility. Agents currently get the server's exact positions of the nearest zombies within 30 tiles (RLBridge `zRadius`, `zMax`), regardless of darkness, vision cone, walls or line of sight, so they see things a human cannot (zombies behind them, in buildings, in the dark). TODO: (1) measure on the real client what fraction of nearby zombies are actually visible to the player by day and by night (client Lua: `IsoGridSquare:isCouldSee(0)` / light level of the zombie's square / vision cone); (2) if most are hidden at night, restrict the published zombie list to visible zombies plus a coarse "heard" cue, on both backends; (3) CONTROL THE TIME OF DAY in experiments: the server world has been running for days, so recent fights and tests were spread across day and night, and real zombies' sight depends on light; check the server's DayLength/StartTime and freeze or fix the hour for tests (a likely source of the large episode-to-episode variance in real fights). Sandbox has "Darkness During Night" and the wiki lists traits (Cat's Eyes, Eagle Eyed) and panic/tiredness that narrow the vision cone.
00000. USER IDEA (2026-10-26): record a real player. The user noticed the scripted fighter never moves while fighting (it only stands and swings), while a real player keeps moving (kiting, stepping back, repositioning) to stay safe. Human demonstrations would give a better teacher than the scripted charge policy and would show which movement habits matter. Plan: (1) the bridge already publishes the same observations for ANY connected player, so a human who joins our local server (as the user did earlier with their own client) can be recorded with a small script (`scripts/record_demo.py --user NAME`: obs stream to logs/demos/*.jsonl); (2) actions are inferred per step from the position change (one of 8 compass moves or stay) and attack events (add the player's attack state to the bridge's published fields; check that the server can see it for a remote player); (3) behaviour cloning on the human data plus DAgger on the real client (the human cannot relabel online, so relabel with the cloned policy's own training distribution and fine-tune with RL); (4) also compare fake-world statistics (stand-off distance, movement while fighting) against the human's to improve the fake backend. A zombie bite is always eventual death (infection kills the character within hours to a couple of days even at full health); a scratch has about a 33% chance to be as bad as a bite; falls, muscle strain and similar are always recoverable. The reward currently only sees the bridge's `getBodyDamage():getHealth()` drop.
