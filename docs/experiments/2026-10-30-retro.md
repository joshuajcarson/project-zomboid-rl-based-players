# Retro cards (RECONSTRUCTED from docs/journal.md and docs/headless-client.md on 2026-10-30)

These experiments ran before the card rule existed. Pre-registered criteria were not written down in advance, so each card says what the criterion implicitly was and where the data is. Raw per-episode data: `results/experiments-2026-10-30/` (README there lists each file). Analyse with `python scripts/compare_arms.py <file>`.

## R1 Headless client: drop the world draw (hour 1)
- Date: 2026-10-30 07:50-08:37. Milestone: M6 (client memory budget) / M9 (speed); original aim: a cheaper real client.
- Question: can the real client run without drawing, and does that cut CPU/RAM?
- Design: agent option `norender` (global, hung login) then `norender=world`; 8-9 episodes each vs a normal client, `charge:1.8:0`, fight-v4. Pre-registration: none (exploratory). Implicit success: client keeps playing AND resource use drops clearly.
- Data: `h1_baseline_render_on.jsonl`, `h1_world_draw_off.jsonl`; notes in `docs/headless-client.md`.
- Result: plays on (kills 1.00 vs 1.25, damage 39.6 vs 40.4, swing timing and hit rates equal, small n) but NO resource saving (1.11 vs 1.14 cores, 4.2 vs 3.8 GB); window goes Not Responding; global render skip freezes login.
- Verdict: FAILURE for the resource goal, SUCCESS for "drawing can be removed". Learnings: the 1-core load is the frame limiter spinning, not work; menus run inside render; ZombieBuddy not needed for one-off patches (conditional patches would be easier with it; untested).
- MILESTONE IMPACT: closed the "headless by draw removal" track (listed in milestones); M6 stays open (memory options untested).

## R2 Real client at 2x/4x game clock (hour 2)
- Date: 2026-10-30 08:41-09:40. Milestone: M9 (parked speed-up).
- Question: does a client clock patch give 2x episodes per wall minute with equal fights?
- Design: server and client `TimeScale` 2 (and 4), `PZ_SETTLE` multiplier on reset waits, 8-24 episodes, `charge:1.8:0`. No pre-registered thresholds. Implicit success: fight results equal to 1x within noise.
- Data: `h2_2x_settle1_broken`, `h2_2x_settle2_10eps`, `h2_4x_settle4_broken`, `h2_2x_settle2_24eps`.
- Result: game time exactly 2.00x wall, ~2x throughput; first 2x run collapsed because reset waits (counted in game time) halved in real time; with PZ_SETTLE=2 a 24-episode run gave 1.25 kills / 56.8 dmg (16 real) vs same-day 1x 1.57 / 49.9 and earlier 1x 1.74 / 25.7: not separable (blocks drift). 4x broken.
- Verdict: INCONCLUSIVE for 2x fidelity; FAILURE for 4x. Learnings: any wait tied to loading/networking is real time (scale with PZ_SETTLE).
- MILESTONE IMPACT: M9 added and parked; needs a paired (interleaved or two-session) test with 60+ episodes per arm before reopening.

## R3 Latency hypothesis for the 2x difference (hour 3)
- Date: 2026-10-30 10:01-10:50. Milestone: M9.
- Question: does extra control latency explain worse 2x fights?
- Design: 1x with +300 ms command delay (11 real) vs same-block 1x control (8 real). Implicit success: delay reproduces the 2x damage increase.
- Data: `h3_1x_plus300ms`, `h3_1x_control`.
- Result: +300 ms 1.36 kills / 43.7 dmg; control 1.57 / 49.7; 2x 1.25 / 56.8. No effect distinguishable; the control block itself was worse than the morning blocks.
- Verdict: INCONCLUSIVE (hypothesis unsupported, power too low). Learnings: block-to-block differences were as large as any effect studied; led to the drift hunt. A latency probe (`goto` effect time) was flawed (1 of 16 trials registered): do not rely on it.
- MILESTONE IMPACT: modify M0 (measurement trust: interleaved arms, 30+ episodes), keep M9 parked.

## R4 Drift hunt A: time of day (noon vs 1 AM)
- Date: 2026-10-30 11:39-12:50. Milestone: M0.
- Question: is darkness the cause of the block-to-block damage drift?
- Design: interleaved arms in one session, server clock per arm (noon vs 1 AM), corpses cleared in both, 20 real episodes per arm, `charge:1.8:0`. Two earlier versions were flawed (arm B clock reverted to the server's; kept as records). Implicit success: arms differ by more than noise.
- Data: `drift_noon_vs_1am.jsonl` (clean), `drift_dark_v1_flawed.jsonl`, `drift_arm_v1_flawed.jsonl`, `drift_noon_cleared_pool.jsonl`.
- Result: noon 1.30 kills / 31.4 dmg, 1 AM 1.35 / 32.7, damage difference 1.3 (se 7.3, z 0.18), 0 deaths in 40.
- Verdict: darkness has NO detectable effect (clean null). Learnings: server clock is authoritative; client-only clock changes revert; server-side body removal does not reach the client.
- MILESTONE IMPACT: none (informs protocol: fix time of day to noon only for reproducibility).

## R5 Drift hunt B: corpses (cleared vs 250-body pile)
- Date: 2026-10-30 12:50-13:31. Milestone: M0.
- Question: do ~230 corpses on the field worsen fights?
- Design: interleaved arms, noon in both, arm A corpses cleared, arm B cleared then 250 fresh bodies laid (`pile`), 17 vs 19 real episodes, `charge:1.8:0`.
- Data: `drift_cleared_vs_pile250.jsonl`.
- Result: cleared 1.82 kills / 24.5 dmg (1 death); pile 1.58 / 34.9 (3 deaths); damage +10.4 (se 8.3, z 1.25), kills -0.24 (se 0.22, z -1.12).
- Verdict: INCONCLUSIVE (direction as hypothesised). Learnings: all 12 deaths in earlier blocks happened with ~230 bodies present; per-episode damage sd ~27 with a heavy tail; frame rate was a flat 30 fps in every block (load is not a factor).
- MILESTONE IMPACT: M0 gains the corpse invariant (clear when >~50 bodies within 35 tiles); a 3x larger corpse test is optional.

## R6 Swing start distance (10-29/30) and R7 retreat on the clean field (10-28/29)
- Milestone: M1 (scripted fighter). Design: `charge:1.3/1.8/2.2/2.6/3.0:0` and `charge:1.8:35` vs `1.8:0`, fight-v4, 20-30 real episodes per policy, run in sequential blocks (NOT interleaved). No pre-registration.
- Data: `results/ledger.jsonl` rows (setup tags field5377-v4, field5377-v4-r2); journal sections of 10-29 and 10-30.
- Result: 1.3 clearly worse (1.09 kills / 55.5 dmg), 3.0 worse (1.35 / 41.6), 1.8-2.6 equal within noise; retreat <35 hp no better (1.36 / 31.6 vs 1.33 / 30.1).
- Verdict: only the large effects stand (FAILURE for 1.3 and 3.0 as improvements); everything else INCONCLUSIVE (cross-block design).
- MILESTONE IMPACT: M1 acceptance made two-session; scripted tuning deprioritised.
